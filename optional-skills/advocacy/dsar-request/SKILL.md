# DSAR Request — Burgess Principle

Help users exercise their right to access personal data held by any organisation, combined with the Burgess Principle question about human review.

## When to Use

- User wants to know what data an organisation holds about them
- User suspects automated profiling or scoring without human review
- User wants to challenge a decision by first understanding what data informed it
- User mentions GDPR, DSAR, subject access request, data access, or "what do they know about me"
- User has received an automated decision and wants the underlying data

## Procedure

1. **Gather details** — Ask for: the organisation's name, the user's relationship with it (customer, employee, citizen, etc.), and any reference numbers or account identifiers.
2. **Determine jurisdiction** — Ask where the user is based. This determines which law applies:
   - **UK**: UK GDPR + Data Protection Act 2018 (Article 15 access right)
   - **EU**: GDPR Article 15
   - **USA**: CCPA (California), state privacy laws, or sector-specific rules
   - **Australia**: Privacy Act 1988, Australian Privacy Principles
   - **Canada**: PIPEDA or provincial equivalents
   - Other: identify the local data protection framework
3. **Draft the DSAR** with the following structure:
   - Subject line: "Data Subject Access Request — [User Name] — [Reference]"
   - Legal basis: cite the relevant article/section
   - Request: all personal data held, processed, or shared about the user
   - Burgess Principle addition: "I also ask you to confirm whether a human member of your team personally reviewed the specific facts of my case before any automated decision was made affecting me, as required under [Article 22 GDPR / equivalent]."
   - Format preference: electronic, machine-readable format
   - Response deadline: 30 days (UK/EU GDPR standard) or as applicable
   - Identity verification offer: state willingness to verify identity if needed
4. **Include specific data categories** the user wants:
   - Communication records (emails, calls, letters)
   - Decision records (approvals, denials, scores, flags)
   - Profiling data (risk scores, categories, segments)
   - Sharing records (who the data was shared with and why)
   - Automated decision logic (Article 22 — meaningful information about the logic involved)

## Tone Guidelines

- **Formal but accessible** — Legal rights, plain language
- **Specific** — Reference the user's actual situation and identifiers
- **Firm** — This is a legal right, not a favour
- **Non-threatening** — State the right, request compliance, mention the regulator only if needed

## Verification

- The DSAR cites the correct legal framework for the user's jurisdiction
- The Burgess Principle question is included alongside the data access request
- Specific data categories are listed (not just "all data")
- A response deadline is included
- The tone is formal, clear, and respectful
